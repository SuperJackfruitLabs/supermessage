# Localization: where the strings actually are

Nothing in this repository is localized. No `strings.xml`, no `.xcstrings`,
no i18n library in `package.json`, no locale anywhere in the Rust core. Every
user-facing word is an English literal at the point it is drawn.

This is an audit and a decision, not a plan of work. Making it real needs a
product answer first — which locales, and whether right-to-left is in scope —
and that answer changes enough of the shape below that guessing it would be
worse than leaving the gap visible.

## 1. What there is to translate

| | Distinct literals |
|---|---|
| iOS (`apple/`, previews excluded) | 49 |
| Android (`app/src/main`) | 46 |
| Web (`src/lib/components`) | at least 14 |
| **Rust core** | **13 rendered strings + 15 membership verbs** |

The web figure is a floor: its copy sits in Svelte markup rather than in a
call this could count exactly.

The last row is the interesting one, and it is the reason this document
exists rather than three tickets.

## 2. The core emits English, and this project's first rule says it should not decide

`AGENTS.md` is blunt about the boundary: **the app parses nothing and decides
nothing.** Localization pushes against that from the other side — the *app*
is where locale lives, and the core is where the sentence is currently built.

The core is already half right, and the half that is right shows how to fix
the half that is not.

### 2.1 Membership lines are already localizable, today

`item_view::membership_verb` maps fifteen Matrix membership transitions onto
fifteen English phrases — "joined the room", "was removed and banned",
"withdrew their request to join". Those are the single largest enumerable set
of core-emitted prose in the project.

They are **not** a blocker, because the core hands hosts both halves:
`TimelineRow.membership_verb` carries the English, and `TimelineRow.item
.detail` carries the machine-readable kind (`"joined"`, `"kickedAndBanned"`)
that the English was derived from. A host that wants a Hindi membership line
can switch on `detail` and never look at `membership_verb`. No core change is
needed for any of the fifteen.

`dto.rs` says why the kind is carried separately, and the reasoning is
exactly the one localization needs:

> re-deriving it from a rendered sentence is parsing your own output.

### 2.2 System and placeholder lines are the blocker

`ItemView::System { text }` and `ItemView::Placeholder { text }` carry **only
the rendered English**. The discriminant exists at the point of construction
and is thrown away one line later:

```rust
Some("m.room.encryption") => ItemView::System {
    text: "Encryption enabled".to_string(),
},
```

A host receives `System { text: "Encryption enabled" }`. It cannot know the
line was about encryption without matching on the English, which is the thing
`dto.rs` names as parsing your own output — and it would break the moment
that copy is edited, which its own doc comment says is a product decision
somebody is entitled to make.

Thirteen strings are affected, and they enumerate cleanly:

| Construction site | String |
|---|---|
| `m.room.create` | `"{} created the room"` |
| `m.room.encryption` | `"Encryption enabled"` |
| `m.room.tombstone` | `"This room has been replaced"` |
| `sticker` | `"Sticker"` |
| `poll` | `"Poll"` |
| `liveLocation` | `"Live location"` |
| `callInvite` | `"Call"` |
| `rtcNotification` | `"Call notification"` |
| `redacted` | `"Message deleted"` |
| unknown msgtype | `"Unsupported message ({})"` |
| unknown event | `"Unsupported event ({other})"` |
| timeline start | `"Beginning of the room"` |
| undecryptable | `"Encrypted message — this device has no key for it"` |

**The fix is the pattern the codebase already chose**, applied one level
down: give `System` and `Placeholder` a kind beside their text, exactly as
`TimelineRow` gives `membership_verb` a `detail` beside it. Keep `text` — a
host with no translations keeps working unchanged, and English stays the
fallback rather than becoming a special case.

It is deliberately **not done here**. Adding a field nothing reads is an
abstraction with no consumer, and it changes a UniFFI enum, which means
regenerating bindings and touching every host that destructures `System`. It
should land with the first host that actually translates something, not
before.

## 3. What each platform would use

- **iOS** — `String(localized:)` and a `.xcstrings` catalogue. It is the only
  option that also feeds App Store localization metadata, and Xcode extracts
  the strings itself.
- **Android** — `strings.xml` under `values-<locale>`. `app/src/main/res`
  already has `values` and `values-night`, so the directory layout is there;
  what is missing is that no string has ever been put in it.
- **Web** — Paraglide (compile-time, tree-shaken, no runtime lookup) suits a
  SvelteKit app better than the runtime alternatives, and its output is
  typed, so a missing key is a build error rather than a blank label.

There is no shared catalogue and there should not be one. Translations are
per-platform files in each platform's native format; the *kinds* they switch
on are what the core shares.

## 4. Order of work

1. **Decide the locales.** Everything below is shaped by it, and RTL in
   particular changes layout work that no amount of string extraction covers.
2. **Extract host strings**, platform by platform. All three are independent
   and none needs the core.
3. **Membership lines**, host-side, off `item.detail`. No core change.
4. **Then** the core change in §2.2, driven by the first host that needs a
   system line in another language.

## 5. What localization will break that string extraction does not fix

Named here because they are the expensive half and are invisible while the
app is English-only:

- **The visual gates will fail, and should.** iOS, Android and web all
  compare pixels against baselines rendered in `en_US`. Translated copy is a
  different length; German compounds in particular will find every fixed-width
  column. See `docs/preview-snapshots.md` and `docs/story-snapshots.md`.
- **Dynamic Type interacts with translation length**, and P4 already found
  what long text does to the decision card at `.accessibility3`. Longer
  translations at large sizes is the same defect class with two multipliers.
- **Dates and relative times** are formatted per-platform today. Both mobile
  gates pin `user.timezone=UTC` and `en_US_POSIX` precisely because these
  formatters are locale-sensitive — which is the gate proving the point.
